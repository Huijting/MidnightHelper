## 1. Waarom deze RFC bestaat

RFC-001 bewees dat Knowledge upstream kan zijn: ChatGPT onderhoudt de kennis, de addon
voert uit. Wat nog niet vastlag, is de *grens*. Deze RFC legt die grens vast en niets
meer: welke vorm de kennis heeft, wie hem inleest, wie de speler-state levert, wie
beslist, en hoe je bewijst dat het klopt voordat een speler het ziet.

De aanleiding voor de strengheid hieronder is de Never Lie Policy. Een aanbeveling is
gevaarlijker dan een tabel: hij stuurt hoe iemand zijn speelavond besteedt. Daarom is
de acceptatie-eis niet "het werkt in-game" maar "negen vastgelegde gevallen geven
buiten de game exact het afgesproken antwoord".

**Scope.** De beslislaag, de kennisvorm, de transpiler, de request-builder en een
debug-uitgang.

**Non-goals in v1.** Geen UI-kaart. Geen wijziging aan de This Week-headline. Geen
tijdinvoer. Geen speler-zichtbare copy. Geen nieuwe activiteitsdetectie. Geen
failure-history. Geen tweede aanbevelingsmotor.

## 2. Architectuur — drie lagen, één richting

```
data/knowledge/*.yaml          upstream, ChatGPT-eigendom, shipt NIET mee
        │
        │  tools/build_knowledge.py          (build-time, Python, atomisch)
        ▼
Modules/KnowledgeData_*.lua     GENERATED, read-only, in de .toc
        │
        ├─► Modules/Knowledge.lua            registry · scope · staleness · gates
        │
        └─► Modules/KnowledgeRuntime.lua
                 ├── BuildRequest()          ENIGE laag die de WoW-API aanraakt
                 └── Evaluate(req, kb)       PURE functie, nul API-calls
                             │
                             ▼
                    /mh know · ns.db.knowledgeProbe      (debug-sink, geen frames)
```

### 2.1 YAML upstream → build-time transpiler → generated Lua

**Besluit.** De YAML blijft de bron van waarheid en wordt bij het committen omgezet
naar een Lua-datatabel. Er komt geen runtime-parser.

**Grond.** WoW's Lua-sandbox heeft geen file-I/O. Een addon kan uitsluitend lezen wat
via de `.toc` als Lua-chunk is ingeladen. Een "loader voor YAML Knowledge Objects" op
runtime kan dus niet bestaan — niet moeilijk, niet onhandig: onmogelijk. Dit is de
enige eis uit het oorspronkelijke backlog-fase-1 die vervalt.

**Uitwerking.**
- `tools/build_knowledge.py` volgt het bestaande patroon van `tools/generate_*.py`.
- Output krijgt een header `-- GENERATED by tools/build_knowledge.py — do not edit`.
- Schrijven is **atomisch** (`.tmp` + `os.replace`). Niet optioneel: de repo *is* de
  live AddOns-map, en op 2026-07-22 logde Rob in tijdens een niet-atomische rewrite van
  `Locales/enUS.lua` — zijn Great Vault-popup toonde ruwe keys. Zie `CLAUDE.md`.
- De transpiler valideert tegen `ko_schema_v0.3` en faalt hard bij een schendig. Een
  object dat niet valideert komt niet in de output; het wordt niet "zo goed mogelijk"
  omgezet.
- De transpiler draait **bij het committen**, niet bij het packagen. De
  BigWigs-packager draait geen Python.

### 2.2 Pure evaluator zonder WoW API-calls

**Besluit.** `Evaluate(request, knowledge) → response` doet geen enkele aanroep naar de
game. Geen `C_*`, geen `Unit*`, geen `GetTime`, geen `time()`, geen globals uit de
client.

**Grond.** Alleen dan draaien de negen fixtures buiten de game, met plain `lua`, in CI
en lokaal. Dat is wat de acceptatie-eis in §8 überhaupt haalbaar maakt. Het is ook de
enige manier waarop een beslisfout reproduceerbaar is zonder dat Rob in-game moet gaan
staan.

**Consequenties die dit oplegt.**
- Tijd is een *input*, geen aanroep. De evaluator mag nooit zelf de klok lezen — ook
  niet voor `fallback_date`. De request-builder levert wat nodig is.
- Willekeur bestaat niet. Gelijke request + gelijke kennis = gelijk antwoord, altijd.
- De evaluator gooit niet. Een onbekende operator of onopgeloste ref is een
  *validatiefout bij build-time*, geen runtime-uitzondering.

### 2.3 Request-builder als enige clientlaag

**Besluit.** Alle toegang tot de client zit in `BuildRequest()`. Wat de client niet
weet, wordt `null` — nooit een aanname die als feit doorgaat.

Bestaande bronnen die de builder gebruikt, allemaal al in de repo aanwezig:

| Requestveld | Bron in de repo |
|---|---|
| `interface` | `GetBuildInfo()` — `Modules/SeasonTransition.lua:23` |
| `mythic_plus_season_id` | `C_MythicPlus.GetCurrentSeason()` — idem; gaf **17** op live |
| `weekly_reward_state.great_vault_reward_ready` | `C_WeeklyRewards.HasAvailableRewards()` — `Modules/VaultReminder.lua:78`, `Modules/ResetRoutine.lua:230` |
| `player_state.item_level` | `GetAverageItemLevel()` — `Modules/AltOverview.lua:252` (moet als `ns.*` geëxporteerd worden) |
| `player_state.role` / `specialization` | `GetSpecialization` — `Modules/KeybindAutoMap.lua`, `Modules/RoleAcademy.lua` |
| `activity_states[ritual_site].available` + prerequisites | `Modules/RitualSites.lua` — weekly 95843, introketen 94380 → 94381 → 96080 → 94382 → 94383 |
| `recent_activity_history` | `ns.db.delveLog[guid]` — `Modules/DelveHistory.lua:133`; `ns.db.ritualLog[guid]` — `Modules/RitualLog.lua:38` |
| `activity_states[].estimated_minutes` (`source: observed`) | duur per run uit dezelfde twee logs |
| `available_session_minutes` | **niet observeerbaar** → altijd `null` in v1 |
| `live_recommended_item_level` | **geen bekende API** → altijd `null` tot gemeten, zie §9 |

**Geen character-GUID en geen timestamp in de request** (contract v0.2). Intern keyen we
op GUID; die hoort niet in een datastructuur die we dumpen en delen.

## 3. Kennisvorm

### 3.1 Outputs-map en externe output-refs

**Besluit (B1).** Elk Knowledge Object heeft `outputs:` — een map van stabiele
output-ref naar een volledig outputblok (`status`, `title_key`, `why_key`,
`first_action_key`, `not_now_keys`, `confidence`).

Een rule-resultaat mag precies één van deze drie vormen hebben:

| Vorm | Betekenis |
|---|---|
| `output_ref: <ref>` | resolveert **binnen** het eigen object; bestaat de ref niet, dan faalt de build |
| `external_output_ref: { object_id, output_ref }` | expliciet een ander object; beide velden verplicht |
| `pass_through: true` | dit object beslist niets; de volgende laag in de pipeline is aan zet |

**Grond.** In v0.2 verwezen rules naar refs (`ritual_t5`, `unknown`, `ask_time`) terwijl
elk object maar één `output:`-blok had. Daardoor eiste fixture 08 van RITUAL-TIER de
status `unknown` terwijl dat object `conditional` declareerde, en verwachtten fixtures
07/08 copy-keys die aan een ánder object toebehoorden. Zes van de negen fixtures waren
niet reproduceerbaar; dit was de hoofdoorzaak.

**Validatie bij build-time.** Elke lokale ref bestaat binnen het object. Elke externe
ref verwijst naar een bestaand object *en* een bestaande ref daarbinnen. Cyclische
externe refs zijn verboden.

### 3.2 Contextuele materialiteit

**Besluit (B2).** Elk inputveld draagt `materiality: material | secondary | contextual`.
De resolutie is deterministisch en in deze volgorde:

1. Een expliciete `missing_input_effect` op de vurende rule wint.
2. Statisch `material` of `secondary` wordt direct gebruikt.
3. `contextual` is **material** wanneer geen enkele nog toepasselijke rule zonder dat
   veld tot een geldige output kan komen.
4. `contextual` is **secondary** wanneer minstens één nog toepasselijke rule zonder dat
   veld nog een geldige output kan leveren.

**Grond.** In v0.2 misten fixture 02 en 08 hetzelfde veld
(`live_recommended_item_level`) en verwachtten tegengestelde confidence — `medium`
respectievelijk `unknown`. Zonder deze regel is dat een contradictie; met deze regel is
het uitlegbaar: in 02 blijft de Tier-5-route open, in 08 kan geen enkele tierregel meer
vuren.

**Waarom dit niet in de evaluator gegokt mag worden.** Regel 3 en 4 vragen: "kan een
nog toepasselijke rule resolveren zonder dit veld?" Dat is een vraag over de
*regelverzameling*, niet over de request. De evaluator moet die dus expliciet
uitrekenen — één pass over de resterende rules — en niet afleiden uit het aantal
ontbrekende velden. Twee ontbrekende velden is geen bewijs van materialiteit.

### 3.3 Derived predicates

**Besluit (B4).** Afgeleide predicaten bestaan alleen als ze in `derived:` gedeclareerd
staan. Een rule die een niet-gedeclareerd predicaat gebruikt, faalt de build.

V1-definities, overgenomen uit `DECISIONS_AND_GO.md`:

| Predicaat | Definitie |
|---|---|
| `recent_success_tier_5` | minstens één voltooide `ritual_site`-run met `tier >= 5` in de aangeleverde `recent_activity_history` |
| `recent_success_tier_6` | idem met `tier >= 6` |
| `first_actionable_prerequisite_exists` | minstens één prerequisite met `actionable == true` |

**Het history-venster is exact wat de addon aanlevert: maximaal 20 voltooide runs.**
Geen tijdvenster. Geen failure-afleiding in v1. Dat getal is geen keuze van deze RFC —
het is `MAX_RECENT = 20` in `Modules/DelveHistory.lua` en `Modules/RitualLog.lua`, en
het venster is dus per definitie gelijk aan wat er al gelogd wordt. Verandert dat
getal ooit, dan verandert het venster mee en moet de KO-definitie mee bijgewerkt worden.

`material_input_missing` en `secondary_input_missing` zijn **evaluatorresultaten**, geen
requestvelden en geen derived predicates. Ze worden nooit uit de request gelezen.

### 3.4 Bindende game_scope

**Besluit (C3).** `game_scope` is bindend. Valt de client buiten de scope, dan doet het
object niet mee — er wordt niets gedegradeerd en niets gemeld vanuit dat object.
`staleness` wordt daarná toegepast, binnen de scope.

TIMEBOX, CONFIDENCE en PREREQUISITE dragen géén `season_ids`: het zijn
versie-onafhankelijke policies. In v0.2 hadden ze `interface_max: null` (dus tijdloos)
naast `season_ids: [17]` (dus S1-only) — twee mechanismen die elkaar tegenspraken.

### 3.5 Engine-owned stale output

**Besluit (B3).** Een stale object voedt nooit zelf een aanbeveling. De melding is
engine-eigendom: object `MH-KO-SYSTEM-STALE-000`, output `stale_knowledge`.

- Versiegebonden activity-KO's krijgen `on_stale: degrade_to_unknown`.
- De response draagt `stale_object_ids` met de objecten die stale bleken, en
  `knowledge_object_ids: ["MH-KO-SYSTEM-STALE-000"]` als bron van het antwoord.

**Grond.** `on_stale: disable` en "het object staat in `knowledge_object_ids`" sluiten
elkaar uit: iets wat uit is, kan geen bron zijn. En de vier `MH_KO_STALE_*`-keys stonden
in het copy-catalogus zonder eigenaar, waardoor de approval-gate ze niet kon
valideren. Beide zijn hiermee gesloten.

**Staleness-signalen (verifieerbaar, niet op de kalender).**

| Signaal | Waarde | Leesbaar via |
|---|---|---|
| `interface` | `>= 120100` | `GetBuildInfo()` |
| `mythic_plus_season_id` | `> 17` | `C_MythicPlus.GetCurrentSeason()`, S1 = 17 in-game gemeten 2026-07-19 |
| `fallback_date` | `2026-08-18` | **alleen vangnet** |

De datum 18 augustus is een community-projectie; Blizzard heeft niets aangekondigd.
Status `COMMUNITY_REPORTED`, dus niet speler-zichtbaar en nooit leidend zolang een
game-signaal beschikbaar is. En: `18` als S2-season-id in fixture 09 is een
*testwaarde*. De echte id is onbekend (`ns.SEASON2.mplusSeasonId = nil`) en mag nergens
als constante landen.

### 3.6 EDITORIAL_REVIEWED

**Besluit (C5).** Nieuwe bronstatus `EDITORIAL_REVIEWED`: onderhouden productmetadata,
expliciet geen Blizzard- of API-feit, speler-zichtbaar na review en goedkeuring.
`ADDON_RESEARCH` houdt exact zijn bestaande betekenis uit `docs/EVIDENCE_REGISTER.md`:
afgelezen uit de data van een andere geïnstalleerde addon.

`interruptibility` draagt voortaan `EDITORIAL_REVIEWED`.

**Grond.** In v0.2 kreeg `ADDON_RESEARCH` de betekenis "reviewed editorial metadata".
Daarmee had één token twee betekenissen in twee documenten — precies het soort drift
waar het evidence-register tegen bestaat. Interruptibility `low` voor ritual en delve
is oprecht redactioneel én stuurt een aanbeveling; dat verdient een eigen label in
plaats van te lenen van een status die iets anders bewijst.

`docs/EVIDENCE_REGISTER.md` krijgt de nieuwe status in zijn statuslijst.

## 4. Request-mapping

**Besluit (C2).** Er is één expliciete `request_mapping`-tabel. Geen impliciete
naamconventie, geen afleiding uit het KO-pad.

```
ko_path                                 →  request
ritual.available                        →  activity_states[activity_id=ritual_site].available
ritual.available_tiers                  →  activity_states[activity_id=ritual_site].available_tiers
ritual.live_recommended_item_level      →  activity_states[activity_id=ritual_site].live_recommended_item_level
ritual.weekly_extra_value_available     →  activity_states[activity_id=ritual_site].weekly_extra_value_available
ritual.interruptibility                 →  activity_states[activity_id=ritual_site].editorial.interruptibility
weekly_reward.great_vault_reward_ready  →  weekly_reward_state.great_vault_reward_ready
player_goal                             →  player_goal
available_session_minutes               →  available_session_minutes
recent_activity_history                 →  recent_activity_history
```

Elk KO-input dat een requestveld leest, draagt een `mapping_key` die in deze tabel
bestaat. Ontbreekt de key, dan faalt de build. Zie O5 voor de entries die nog missen.

**Engine-geïnjecteerde inputs.** Twee inputs komen niet uit de request maar van de
engine, en worden als zodanig gemarkeerd:

- `stale_object_ids` — bepaald door de staleness-gate, gevoed aan `MH-KO-SYSTEM-STALE-000`.
- `manual_disable_flag` — engine-eigendom (C4), backing `ns.db.knowledge.disabled[object_id] == true`.

Ze staan niet in de request-mapping en mogen niet uit een request gelezen worden.

## 5. Evaluatiesemantiek

### 5.1 Drie-waardige logica — GOEDGEKEURD 2026-07-30

`nil`/`null` betekent **onbekend**, en onbekend is niet gelijk aan `true` en niet aan
`false`. Een vergelijking met een onbekende waarde vuurt dus niet automatisch. Een rule
met `estimated_total_exceeds_available_time: true` vuurt niet wanneer de bovengrens
onbekend is — hij vuurt alleen bij een bewezen `true`.

Dit is geen nieuwe uitvinding: het is exact het contract van `ns.Aura`
(`Modules/Auras.lua`) — `true` / `false` / `nil = onleesbaar ≠ afwezig`. Dezelfde
denkfout ("leeg dus niet zo") kostte daar al een ronde.

### 5.2 Pipeline en arbitrage

Contract v0.2 herhaalt de pipeline niet, dus de enige vastgelegde volgorde is die uit
v0.1 — en die zet `apply_timebox` **vóór** `apply_activity_specific_rules`. Dat kan
niet: fixtures 02 en 03 hebben `available_session_minutes: null` en verwachten een
ritual-route, terwijl TIMEBOX priority 1 juist op `null` vuurt en dan `ask_time` zou
opleveren.

**Vastgelegde volgorde — GOEDGEKEURD 2026-07-30** (wijziging t.o.v. contract v0.1).
Het besluit in één regel: *kies eerst een inhoudelijk geldige route; pas daarna werkt
Timebox als gate op die gekozen route; Timebox mag alleen zelf een output geven wanneer
geen route verantwoord kan worden vervolgd.*

1. **Scope + freshness** (engine). Buiten scope → object doet niet mee. Stale →
   `degrade_to_unknown` en het id in `stale_object_ids`.
2. **Goal.** `player_goal` uit de request; in v1 altijd `progress` met
   `assumed_inputs: ["player_goal"]`.
3. **Niet-beschikbare activiteiten verwijderen.**
4. **Prerequisites** (PREREQUISITE). Blokkeert het? Dan is dat het antwoord.
5. **Activity selectors** (RITUAL-TIER en later meer).
6. **Timebox** als *gate* op de gekozen route. TIMEBOX levert alleen een **eigen**
   output wanneer stap 5 geen route opleverde.
7. **Ranking.** In v1 triviaal: er is ten hoogste één selector.
8. **Confidence** (CONFIDENCE) met `known_inputs`, `missing_inputs`, `stale_inputs`,
   `assumed_inputs`.
9. **Precies één volgende stap** plus `not_now`.

Stap 6 is de arbitrageregel die fixtures 02, 03 en 04 onderling consistent maakt: bij
een verantwoord te vervolgen route wint de route, bij géén route mag de timebox spreken.

### 5.3 Eén aanbeveling

Er wordt ten hoogste één primaire aanbeveling geretourneerd. Niet "meestal één" — de
evaluator kan er structureel niet meer produceren, omdat stap 9 op één output uitkomt
en alle overige objecten via `pass_through` of `external_output_ref` naar díe ene
output leiden.

## 6. Eigendom van de headline

**Besluit (productbesluit ChatGPT, bevestigd).** `ns.GetNextWeeklyAction()`
(`Modules/ResetRoutine.lua:781`) blijft eigenaar van de ene primaire This
Week-headline. Knowledge is in v1 **geen tweede motor**.

Wat Knowledge levert: uitleg, eerste handeling, `not_now`, confidence en eerlijke
fallback. Later mag `GetNextWeeklyAction` Knowledge intern gaan gebruiken; dat is een
apart besluit en valt buiten deze RFC.

**Grond.** De functie bestaat, levert al precies één stap uit een prioriteits-geordende
live lijst, en wordt al geconsumeerd door `Modules/HomeDashboard.lua:243`. Twee motoren
op dezelfde tab geven twee antwoorden op dezelfde vraag. Het restart-pakket verbood
zelf al "een los tweede systeem naast de bestaande addonarchitectuur".

## 7. State en migratie

Knowledge Objects gaan **niet** in SavedVariables. Ze zijn release-data, geen
gebruikersstaat: ze horen in de gegenereerde Lua die met de versie meeschuift.

Wat wél in `ns.db` komt, volgt de bestaande strategie uit `Core.lua:241-276`:
`CURRENT_SCHEMA_VERSION` plus een geordende, idempotente `MIGRATIONS[]`-tabel die vóór
`MergeDefaults` draait.

| Key | Inhoud |
|---|---|
| `ns.db.knowledgeProbe` | laatste request + response uit `/mh know save` (debug) |
| `ns.db.knowledge.disabled[object_id]` | handmatige uitschakeling (C4) |

Twee regels die daarbij niet onderhandelbaar zijn:

- **Nooit een lijst als default in `DEFAULT_DB`.** `MergeDefaults` merget lijsten per
  index, waardoor een door de gebruiker verwijderde entry eeuwig terugkomt. Dat is
  waarom `db.favourites` op afroep wordt geschreven (`Core.lua:234-239`).
- Elke schemawijziging = één nieuwe migratiefunctie plus een versiebump. Migraties zijn
  idempotent en draaien in `pcall`.

## 8. Acceptatie

Een Knowledge Object is pas speler-zichtbaar wanneer élk van deze punten geldt
(`approval_gate` uit `ko_schema_v0.3`):

- `status == approved` — `review` betekent **niet speler-zichtbaar**, en alle objecten
  staan vandaag op `review`
- `source_status` is speler-zichtbaar volgens `source_status_policy_v0.2`
- alle output-refs resolveren, lokaal en extern
- alle derived predicates valideren
- alle `copy_keys` bestaan in enUS **en** nlNL
- het object is niet stale
- de volledige request/response-fixtures slagen

**Harde poort voor de implementatie:**

| Eis | Waarde |
|---|---|
| Fixtures | **9/9** groen, buiten de game, met plain `lua` |
| `tools/lint_addon.py` | **HARD = 0** |
| `luac -p` | schoon op elk aangeraakt bestand |
| Nieuwe lint-check (C8) | **verplicht** — elke gegenereerde copy-key bestaat tijdens build/CI in enUS én nlNL |

Die laatste check is bevestigd verplicht (2026-07-30) en nodig. Onze linter vangt vandaag een key die in *code*
wordt aangeroepen maar niet bestaat (HARD check 1). `copy_keys` komen als **data** in
een gegenereerde tabel, niet als literale `ns:L("…")`-aanroep — de linter ziet ze dus
niet, en een ontbrekende key zou als ruwe key op het scherm eindigen. Exact het
22-juli-scenario, langs een andere weg.

**Geen runtimecode voordat deze RFC is goedgekeurd door Rob en ChatGPT.**

## 9. Risico's, onbekenden, API-beperkingen

**Live aanbevolen itemlevel — onbekend.** Nergens in de repo wordt zo'n waarde uit de
client gelezen. Wat er is: een hardcoded `DELVE_LOOT_TABLE` in `Modules/Delves.lua:233`,
expliciet gelabeld "UI hint only", en `C_DelvesUI.GetActiveDelveTier`
(`Modules/DelveBossShowcase.lua:1175`) dat alleen *binnen* een delve werkt en een tier
teruggeeft, geen aanbevolen ilvl. Voor ritual-tiers is geen API bekend. Het veld blijft
`null` tot een meting het tegendeel bewijst.

De meting gebeurt met een **enumererende** probe in de stijl van `Modules/ApiProbe.lua`:
die dumpt wat de client daadwerkelijk heeft, in plaats van een gegokte naam te testen.
Het verschil is belangrijk — een probe op een verzonnen naam "vindt niets" om twee
verschillende redenen en je kunt ze niet onderscheiden.

**Sessietijd — niet observeerbaar.** De addon kan niet weten hoeveel tijd iemand heeft.
V1 doet geen invoer en geen aanname: `null` in, `ask` / `low` uit.

**`player_goal` — aangenomen.** V1 gebruikt `progress` en zet `player_goal` in
`assumed_inputs`. Confidence kan daardoor nooit `high` worden wanneer het doel de
uitkomst materieel beïnvloedt. `vault_only`, `learn` en `relax` blijven volledig
testbaar via fixtures maar zijn niet via de live UI bereikbaar. Gevolg dat expliciet
benoemd moet worden: **fixture 02 kan in v1 in-game niet voorkomen**, want die vereist
`vault_only`.

**Mislukkingen worden niet gelogd.** `Modules/RitualLog.lua` logt bewust alleen
voltooide runs; een afgebroken run verdwijnt. `DECISIONS_AND_GO.md` laat failure-history
vallen als required input, dus dit blokkeert v1 niet — maar het betekent dat het
reliability-model in v1 alleen op successen leunt en dat een reeks mislukkingen
onzichtbaar blijft. Wanneer dat later wél gewenst is, hoort het in de bestaande
`{ lifetime, recent }`-ring, niet in een nieuwe SV-tak.

**Patch 12.1.** Twee dingen om in het oog te houden, geen van beide een blocker voor
fase 1 omdat die geen frames maakt: rolesets kunnen een frame onzichtbaar houden
ondanks `:Show()` (vandaar `/mh roleset`), en auras worden secret — gemeten
`ShouldAurasBeSecret = false` op de RC-build voor je eigen auras, groepsleden ongetest.

**Timing.** De versiegebonden KO's verlopen bij de S2-start. 2.12.0 is de
patch-compatibiliteitsrelease en 3.0.0 de seizoensrelease; een Knowledge-feature haalt
die realistisch niet, en hoeft dat ook niet. Wat wél moet: het degradatiepad staat er
vóórdat het nodig is.

**Bloat.** De `.toc` laadt al ~200 bestanden. Drie erbij is te verdedigen. Een vierde

## 11. Punten uit de validatie

### 11a. Gesloten — bevestigd 2026-07-30

**O1 — De catalogus is incompleet. BEVESTIGD ALS BLOKKADE VOOR IMPLEMENTATIE.**
`normalized_ko_catalog_v0.3.yaml` bevat drie objecten: `MH-KO-SYSTEM-STALE-000`,
`MH-KO-RITUAL-TIER-1207-002`, `MH-KO-TIMEBOX-1207-003`. Twee daarvan verwijzen via
`external_output_ref` naar CONFIDENCE-004, dus de eis "all output refs resolve" faalt op
de catalogus zelf.

*Besluit: er wordt geen transpiler gebouwd tegen een onvolledige catalogus.* De
definitieve catalogus moet alle zes schema-v0.3-objecten bevatten:

| Object | Aanwezig in v0.3 |
|---|---|
| `MH-KO-SYSTEM-STALE-000` | ✅ |
| `MH-KO-WEEKLY-POWER-1207-001` | ❌ ontbreekt |
| `MH-KO-RITUAL-TIER-1207-002` | ✅ |
| `MH-KO-TIMEBOX-1207-003` | ✅ |
| `MH-KO-CONFIDENCE-1207-004` | ❌ ontbreekt |
| `MH-KO-PREREQUISITE-1207-005` | ❌ ontbreekt |

De v0.2-versies mogen **niet** als tijdelijke vervanging dienen. Ze hebben geen
`derived`, geen `materiality` en één `output:` in plaats van `outputs:` — schema-v0.2-vorm
valideert niet onder v0.3, en een "zo goed mogelijke" omzetting zou precies het soort
stille aanname introduceren waar deze RFC tegen bestaat.

**O2 — Pipeline-orde. GOEDGEKEURD.** `apply_timebox` stond in contract v0.1 vóór de
activity rules, wat fixtures 02 en 03 brak. Vastgelegd in §5.2: eerst een inhoudelijk
geldige route kiezen, dan Timebox als gate op die route, en een eigen Timebox-output
alleen wanneer geen route verantwoord kan worden vervolgd.

**O3 — Attributie van `knowledge_object_ids`. GOEDGEKEURD, met één fixturecorrectie.**
Elk object dat een vurende rule of een geresolveerde output bijdroeg wordt genoemd, in
pipeline-orde. Fixture 08 wordt daarmee:

```
knowledge_object_ids:
- MH-KO-RITUAL-TIER-1207-002
- MH-KO-CONFIDENCE-1207-004
```

Inhoudelijk: het Ritual-object constateert dat geen route betrouwbaar gekozen kan
worden; het Confidence-object levert de uiteindelijke `unknown`-output. Beide dragen bij,
dus beide worden genoemd. Fixture 05 was al conform deze regel.

**O7 — Drie-waardige logica. SEMANTIEK GOEDGEKEURD** (§5.1). Resteert alleen het
opnemen van die ene regel in `ko_schema`, zodat de transpiler er tegen kan valideren in
plaats van dat de evaluator het als conventie draagt.

### 11b. Nog open — blokkeren de transpiler, niet deze RFC

Elk punt heeft een voorgestelde resolutie. Een "ja" per punt is genoeg.

**O4 — TIMEBOX gebruikt vier niet-gedeclareerde predicaten.** `derived: {}` staat leeg,
maar de rules gebruiken `estimated_total_exceeds_available_time`,
`estimated_minutes_max`, `activity_fits_with_buffer` en `prerequisites_met`. Ook het
buffer-model uit cluster 03 v0.1 (`setup + estimate_max + 5 minuten herstelbuffer`) is
bij de normalisatie verdwenen, terwijl `activity_fits_with_buffer` er niet zonder kan.
*Resolutie: alle vier declareren in `derived`, plus het buffer-model expliciet in het
object. Kanttekening: priority 2 (`prerequisites_met: false → pass_through`) is dode
code als prerequisites in stap 4 al zijn afgehandeld — weglaten of de orde aanpassen.*

**O5 — De mapping-tabel is incompleet.** Geen entries voor
`activity.estimated_minutes.max`, `activity.interruptibility` als generiek pad (nu
alleen de ritual-specifieke variant), `prerequisites_met`, `prerequisite_state_known`,
`missing_prerequisites`, `interface`, `mythic_plus_season_id` en `player_state.*`.
*Resolutie: aanvullen, of vastleggen dat een input zonder `mapping_key` per definitie
engine-geïnjecteerd is.*

**O6 — Predicaat-grammatica in `where`.** `derived_shape.operators` noemt
`any/all/count_gte/exists/equals/and/or/not`, maar `where` gebruikt `tier_gte: 5` —
een veldpredicaat, geen operator. *Resolutie: de suffixen `_gte`/`_lte`/`_gt`/`_lt`
vastleggen plus platte gelijkheid, zodat de transpiler `where` deterministisch kan
compileren.*

**O8 — Engine-geïnjecteerde inputs markeren.** `stale_object_ids` en
`manual_disable_flag` staan als gewone inputs. *Resolutie: een veld
`origin: request | engine` op het input-shape.*
